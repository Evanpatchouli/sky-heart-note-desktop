# 旧个人库迁移与核对（P1-03）

旧预约先进入核对清单。只有能确认订单来源、俱乐部、实际派单归属、接收游戏账号和购买数量，并已核对是否重复的记录，才可拟定共享订单映射。原始记录保留在备份和核对报告中。共享订单结构见 [P1-02 共享订单 API](club-orders.md)。

## 准备备份并生成清单

1. 关闭旧桌面端，为每名原所有者保存一份一致可读的 SQLite 备份。若启用了 WAL，使用 SQLite 的备份功能或在确认 WAL 已合并后复制。记录备份批次、文件校验值和原所有者的四位 ID，保留前导零。用账号交接记录核对文件归属。
2. 在仓库根目录运行下列命令。路径和四位 ID 均为示例。脚本只读指定的备份，向标准输出写出 JSON。保管报告时，按原备份相同的权限限制访问。

```powershell
pnpm --dir server exec ts-node scripts/audit-legacy-club-orders.ts 00A1 "C:/backup/a/data.db" 00B2 "C:/backup/b/data.db" > review.json
```

3. 用复核批次的备份对比最初的审核基线。两批须覆盖同一组所有者。报告中的 `differences` 对两张业务表分列新增、移除和同键改动，列出改动字段及前后值。任何改动都应先核对来源与既有映射，再决定如何处理。

```powershell
pnpm --dir server exec ts-node scripts/audit-legacy-club-orders.ts 00A1 "C:/current/a/data.db" 00B2 "C:/current/b/data.db" --against 00A1 "C:/backup/a/data.db" 00B2 "C:/backup/b/data.db" > review-diff.json
```

## 逐项核对

| 核对项 | 操作人要确认的内容 |
| --- | --- |
| 来源键和跨库同号 | 在各自的 `booking`、`songxinhao` 表内，以「原所有者四位 ID + 原表 ID」定位，例如 `booking/00A1:8`。两库同一数字编号仍各自保留，见 `localIdCollisions`。报告中 `localId` 用十进制字符串保留精度，`fields` 保存其余列的原值，包括原始时间戳、状态、数量、文本和金额。 |
| 送心号 | `booking.sid` 只查同一所有者的 `songxinhao.id`。报告列出查到、未填、缺列、值无效或在本库缺失。查到仅证明旧库的引用关系。执行账号纳入共享份额前，核对实际使用者和当单分工。 |
| 派单人与承接成员 | 保留「派派」`paipai` 和「指派」`zhipai` 的原始文本。根据当时的派单记录及成员账号凭据核对创建人、当单派单人、承接人及所属俱乐部。多标签、重名、账号停用和无法核实的关系都留待人工认领。原所有者只标识记录来源。 |
| 老板、接收号和数量 | 「板板」`banban`、标题和备注可供联系核对。查原订单凭据，分别确认平台客户身份、接收游戏账号和购买数量。只有昵称或文本的旧记录交由人工核实客户账号，证据不足时保留原始记录和待核实状态。旧 `total`、应出、实送及今日数据按原值归档，无法核实的数量或口径留在清单。 |
| 疑似同一业务订单 | `possibleDuplicates` 按跨库的「标题 + 日期」或「老板文本 + 日期」列出候选。用原派单或下单凭据交叉核对日期、接收号、购买数量、成员分工及已有共享单。若确认为同一单，登记一个共享订单 ID 及其全部来源键，逐一复核份额和实绩。若为不同单则分别记录理由，仍无结论的候选留待核对。 |
| 历史金额和履约进度 | 保留 `gongzi`、`yuqiJiesuan`、`shijiJiesuan` 和各项旧状态。它们是核对证据，个人余额和团费入账须使用后续确定的正式结算流程。旧「实际结算」在本方案及演练中没有资金写入路径。 |

`manualClaims` 给出每笔预约及其核对项，按来源键查 `rows.booking` 的原字段和 `rows.songxinhao` 的相关账号。候选检索只展示报表内可直接比较的文本，操作人仍要查已有共享订单与原始凭据。记录每个来源键的结论、支持该结论的凭据引用、核对人及日期。旧个人设置 `kv` 继续由单所有者的 [旧库导入脚本](../server/scripts/import-employee-db.ts) 处理，原始备份可随时复核。

## 核对结果如何落地

- 可确认历史来源的记录沿用「直接派单」或「客户端下单」。实际来源和归属凭据不足时留在核对清单。历史直接派单的发起人与当单派单人需要核对到同一账号。客户归属、已派发状态、承接份额和履约明细分别核对凭据。承接、财务复核和正式入账的未决规则见 [送心业务细则](heart-delivery.md#需要业务方确认的决定)。
- 团员为新业务创建直接派单草稿时，可按四位 ID 选择已有客户，或显式新建拥有独立四位 ID 的客户账号。历史记录的客户归属仍需原订单凭据支持。参见 [共享订单的写入与查询](club-orders.md#写入与查询)。
- 若后续执行正式迁移，为每个来源键保存已核对快照和目标订单 ID，并给同一业务订单固定一次共享订单提交标识。一个来源键只能关联一笔共享单。一笔订单可以关联多个已核实的来源键。存储层应分别保证来源键唯一和 P1-02 订单提交键唯一。落地时在同一次事务中保存新订单与来源关系，或对已有共享订单原子补记关系。对同键同内容重试返回既有结果，源内容有差异则输出逐字段差异，交回人工复核。

## 重跑隔离演练

```powershell
pnpm --dir server exec ts-node scripts/rehearse-legacy-club-orders.ts
```

演练需要本机可执行的 `mongod`，可用 `MONGOD_BINARY` 指定完整路径。命令生成两份合成旧库，在系统分配的回环端口启动一次性的 MongoDB 单节点副本集。P1-02 的 `club_orders` 草稿与来源快照在同一事务写入。演练会尝试用新文档 ID 重复写入同一订单提交键，确认实际唯一索引拒绝该写入，并检查目标库仅包含订单与来源集合。命令结束后清理临时文件。

| 演练记录 | 预期结果 |
| --- | --- |
| `00A1:8` | 测试已核对的 50 颗普通单，直接派单草稿，客户平台归属待核实。重跑返回相同订单 ID，目标中仍为一单。旧「实际结算」`¥20.50` 留在原预约快照中。 |
| `00B2:8` | 与甲库预约本地同号，但实际是另一笔。乙库缺少 `sid=18`，甲库的 18 号不可借用。文本派单人、同昵称老板和成员待人工认领。 |
| `00A1:9`、`00B2:9` | 相同标题、老板文本和日期，原文及各自送心号仍可追溯，两条留待核对是否同一笔订单及如何归并。两库各自的 17 号也保留独立。 |
| 修改源库再跑 | `00A1:8` 的备注和 `00A1:17` 的蜡烛数展示前后差异，另列甲库新增的 10 号和移除的 9 号。既有演练草稿与已保存快照仍对应初次核对的内容。 |

输出包括一笔已应用的演练草稿、三条人工核对项和改动前后的差异。
