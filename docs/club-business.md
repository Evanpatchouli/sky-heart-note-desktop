# 俱乐部业务说明

本平台服务于《光遇》俱乐部。老板提出需求并支付报酬，团员组织和交付服务，俱乐部管理订单、团员收益与团费。送心团可以只经营送心。俱乐部还可以经营代跑、陪玩。首期围绕一个俱乐部把送心流程跑通，再逐条接入其他业务线。

本文用“已明确”记录业务方给出的规则，用“建议”标记首版产品设计，用“待确认”标记仍会影响开发或金额的决定。送心的报价、日报、异常和结算算例见[送心业务细则](heart-delivery.md)。交付顺序见[路线图](roadmap.md)，开发进度以[任务清单](todo.md)为准。

## 订单来源

**订单来源只有两种，由谁在哪一端发起决定。派单是两种来源共同的必经环节。**

| 订单来源 | 谁发起 | 谁负责派单 | 如何进入接单流程 |
| --- | --- | --- | --- |
| 直接派单 | 派单人在团员端发起订单 | 发起订单的派单人 | 派单人在团员端主动派发，开放抢单或指派执行团员 |
| 客户端下单 | 老板在客户端提交订单 | 老板主动指定或系统随机指定时，候选均为本俱乐部有效且带“派单”标记的团员。无合格候选时，创建待分配订单，由团长或副团长后续手动分配 | 确定本单派单人后进入待派单。由其主动派发后，才开放抢单或交给指定的执行团员 |

订单详情与统计始终沿用创建时的来源。例如，老板在客户端下单，系统指定青禾负责，青禾随后在团员端发布，这笔订单从下单到结算都归为**客户端下单**。订单另行记录派单人、其确定方式和实际派发状态，便于追溯。

**待分配订单**可由本俱乐部的团长或副团长分配给任一有效团员，选人列表将有效且带“派单”标记的团员排在最前。手动分配仅确定本单归属，无需修改成员的长期“派单”标记。由本单派单人随后主动派发并触发全团通知。

实际分配前，老板可主动取消本人的待分配订单。同一订单的取消与手动分配只能有一个成功，先完成的一方确定最终结果。订单保留“客户端下单”来源和老板归属，有派单人后记录老板指定、系统随机或管理者手动分配的归属方式，手动分配保留经办人及时间。重复提交同一建单请求返回原订单，取消或分配的同一次请求重试返回原处理结果，各动作只生效一次。

## 派单发布通知与接单区

**本单派单人主动发布成功时，系统向发布当时本俱乐部的全体团员发送新派单通知。** 直接派单和客户端下单都在这个时点触发，同一次发布只产生一条业务通知。举例说，老板下单后系统选中青禾，订单此时仍待派单。直到青禾实际发布，才通知全团。未带“派单”标记的团员也在全员通知范围内。

团员端设有独立的**接单区**。团员点击系统通知或站内通知，直接进入接单区并定位到对应订单，查看最新可接份额，再主动点击抢单。公开派发和定向派发都提醒全团。公开份额按抢单结果分配，定向份额仅由被指定的团员承接。如果点开时已经抢完或订单已撤回，接单区展示当前状态，并可继续浏览其他可接订单。

送心单按段记录每次单价、总赠送次数和日量，段内可指定各送心员每日负责次数与预期执行时段。团员抢单申报每日能送的次数，系统按领取先后分配，在段内日余量和全单余量内截量。建单时单列预计实收爱心颗数，接单时单列实际实收爱心颗数，现金收款另记金额。[订单分段](heart-delivery.md#订单分段)

全体团员都有站内通知。已开启系统通知的设备还会收到 Web Push 提醒，点击后进入同一接单区。未开启系统通知或推送延迟时，打开团员端仍可从接单区查看已发布订单。

## 谁在一笔订单中做什么

直接派单时新建的老板可由原建档订单的派单人交付一次性激活链接。老板在客户端自行设置用户名和密码，沿用原四位 ID 查看本人历史订单。[激活步骤](club-orders.md#写入与查询)

| 身份或分工 | 已明确的职责 | 产品需要区分的事情 |
| --- | --- | --- |
| 老板（客户） | 向派单人提出需求，或在客户端自行下单，从本俱乐部有效且带“派单”标记的团员中指定派单人。实际分配前可取消本人的待分配订单。提供接受服务的游戏账号、付款，必要时申请退款。尚未结单时可在原单追加计价段，包括原约定次数已送完的情况 | 平台客户身份和游戏账号分别记录，老板可以查看本人从两种来源产生的订单 |
| 团长、副团长 | 参与俱乐部管理，可查看本俱乐部待分配订单及候选团员，并分配给任一有效团员 | 可确认本团订单的团费额外售后补偿和责任团员罚款申请；其他管理操作的委派范围待确认 |
| 财务 | 参与俱乐部财务管理 | 建议提供收退款核对、订单分账和团费明细。实际收款人、经办人、审核人应可区分 |
| 派单员（本单的派单人） | 发展老板、对接需求、按系统预计价收款、派单与监督进度，可直接改派未送次数。剩余次数的约定单价变化时，提交变更、说明原因并与老板协商，同意则补款续送，拒绝则停送退款。按团规在订单页提出责任团员罚款，或提请团费额外售后补偿。补偿经团长或副团长确认并实际退款后，登记实退。履约完成且金额核平后，由当单派单人确认结单并触发入账 | 直接派单时按用户名、昵称或 ID 选择已有老板，或填新老板昵称由后端建号并关联。派单人设置首段每次派抽，管理员设置每次团抽。整单及后续追加段沿用首段每次派抽与团抽，后台团抽调整仅用于全新订单。完成量和结单状态分别记录 |
| 送心员（本单的接单人） | 抢单或接受指派，使用自己的送心号给老板送心，按日提交实际赠送次数与到账颗数。补报和未入账日报更正提交即生效 | 一单可由多人承接，一人可用多个游戏号。更正保留前后值、经办人、时间和原因。个人收益要能追溯到本人实际赠送次数 |

**每个团员都可以派单和接单，同一笔订单允许自派自接。** “派单”标记用于限定老板指定和系统随机指定的范围，也用于手动分配候选排序。派单人、接单人应记录在具体订单上。改派保留原承接人已送记录，接手人须先注册入团并具有团员或更高身份，团员可发送注册邀请链接。退款暂不强制复核。团长、副团长、财务是组织分工，现有 `admin`、`employee`、`common` 是端的登录权限。具体记录的读写权限取决于俱乐部成员身份、订单关系及管理授权。[送心规则与算例](heart-delivery.md)

## 三条业务线如何共用平台

| 优先级 | 业务线 | 已确定的边界 |
| --- | --- | --- |
| P1 | 送心 | 报价与收款、抢单或指派、送心号关联、每日送心、活动、异常及最终分账 |
| P2 | 代跑 | 先向业务方取得普通单和异常单，再确定服务范围、报价单位、执行记录、验收及结算方式 |
| P3 | 陪玩 | 先取得实际接单和交付案例，再确定预约、计价、履约及异常处理规则 |

建议三条业务线共用俱乐部成员、客户、订单编号、派单人与接单人关系、收退款记录、结算明细和余额流水。订单带业务类型。爱心颗数、蜡烛和送心号属于送心明细。代跑和陪玩的计价单位、交付凭据及状态在各自调研完成后定义。

## 三端与设备

P1 同时覆盖直接派单和客户端下单。在线支付渠道和余额提现方式待确认。

| 端 | P1 的主要操作 | 设备要求 |
| --- | --- | --- |
| 管理端 `admin` | 维护成员与授权、团抽规则。按职责监督订单、处理异常、核对结算与团费 | PC、手机、Pad 均能操作，支持安装为 PWA。小屏表格可切为摘要和详情 |
| 团员端 `employee` | 团长或副团长从「派单准备」处理本俱乐部的待分配订单。团员可直接派单，处理分给自己的客户端订单，报价、登记收款并主动派发。收到新派单通知可进入接单区抢单或接受指派，履约后填日报、查个人余额 | PC、手机、Pad 均能操作，支持安装为 PWA。手机底部 Tab 提供“接单”入口 |
| 客户端 `client` | 提交订单，可指定派单人或在分配前取消本人的待分配订单，查看本人订单的分配与派发状态、活动报价、交付进度及收退款结果 | PC、手机、Pad 均能操作，支持安装为 PWA。手机用底部 Tab 到达下单、查看本人订单和个人入口 |
| 官网 `site` | 面向访客展示俱乐部及服务入口 | 保持公开访问。本轮 PWA 安装范围是上面三个登录端 |

三端移动版采用可安装的渐进式 Web 应用（PWA），原生手机 App 暂缓。底部 Tab 指手机端的**一级导航**。团员端「我的承接」内保留时间轴、列表、日历、表格、看板五个二级视图，共用本人承接订单。建议在 Pad 横竖屏分别验证派单表单、多人分配和财务明细。关键操作要能点按，悬停提示要有可点开的等价入口，拖拽若用于分配则提供点选路径。手机底栏为系统安全区留空间，软键盘收起前后都能完成提交。
