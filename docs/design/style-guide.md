# 两端视觉与交互规范

本稿供 P1 产品、前端和验收共同使用。团员通常同时处理多个订单，需要在队列里比较份额和状态。老板关心自己收到了多少心、付了多少钱、现在需要做什么。因此，团员首页是接单工作台，客户端首页是我的订单。两端采用同一纸飞机标记、“送心手记”字标和业务词汇。[交互原型与预览](README.md)

## 视觉基线

| 项目 | 团员端 · 协作工作台 | 客户端 · 轻量服务页 |
| --- | --- | --- |
| 主色与用途 | 靛蓝 `#355BC1` 用于当前导航、选中订单、抢单与正式派发 | 服务绿 `#196850` 用于进度、主按钮和当前导航 |
| 文字与表面 | 标题与正文 `#1D2A41`、次要说明 `#526477`、画布 `#F4F6F9` | 文字沿用共用色，画布 `#F4F6F5`，已到账区域使用浅绿底 |
| 状态 | 正常完成/可继续用绿色，待确认用琥珀色 `#885510`，失败或风险用红色 `#A23B40`。同时显示状态文字 | 使用老板能读懂的“待确认补差”“已暂停送心”“已退款”。进度条同时写明到账与剩余颗数 |
| 分组与留白 | 白底队列与详情各为一个工作区，用 1px 分隔线（共用边线 `#DBE2EB`）组织行，面板圆角 12px | 每组回答一个问题，优先顺序为交付进度、待我处理、款项与动态。白色分组圆角 12–16px，保留可点按的整行 |
| 字体与数字 | 使用系统中文字体。正文 14–15px、次要信息 12–13px、页面标题 25–34px。单号用等宽数字，单据金额统一两位小数 | 正文 14–16px，到账数量可放大到 40–64px。实际到账标“颗”、实际操作标“次”，金额用 `¥70.00` 这样的格式 |
| 动作层级 | 同一任务区给一个主要动作。列表选中用浅蓝底、位置标记和选中状态，行内可读剩余量 | 涉及补款或退款时优先显示“查看补差方案”。确认页写清行为及后果，“同意补差”“拒绝补差并停送”分别二次确认 |

基础间距使用 4、8、12、16、24、32px，小屏页面左右留白约 14–16px。图标与文字并排使用，实心高亮留给当前任务。输入、列表、状态标签、进度和弹窗在正式实现中可映射到现有 Ant Design 控件并使用局部主题。客户端不因复用控件而引入管理端表格、权限菜单或内部佣金字段。[共享样式变量](prototype/base.css)

## 信息结构与屏幕尺寸

| 设备 | 团员端 | 客户端 |
| --- | --- | --- |
| 手机，宽度 < 600px | 底部「接单 / 派单 / 我的」。队列点入详情，提供返回。通知可直接定位该单 | 底部「订单 / 下单 / 我的」。单列读进度、决定和资金明细，主按钮适合单手点按 |
| Pad，600–1023px | 可收窄一级导航，空间允许时队列和详情并列。约 735px 及以下降为分层阅读 | 顶部导航，利用有效内容宽度选择并排或纵向阅读。表单与金额摘要保持可见和可点 |
| 桌面，宽度 ≥ 1024px | 左侧一级导航，工作区保留筛选与队列上下文，右侧呈现选中订单的最新份额和操作 | 顶部导航，订单事实与待处理事项并列。详情可核对订单动态、原实付及后续补退 |

断点按视口宽度处理，Pad 分屏也应触发重排。一级 Tab 和订单内部视图分开。触摸设备主要动作与导航的目标尺寸建议至少 44 × 44px。窄屏确认弹窗可滚动，底栏预留安全区与内容底部空间。关键操作支持点按和键盘，拖拽、右键、鼠标悬停都有可点开的替代入口。

## 共用组件及其行为

| 组件 | 应展示与处理 |
| --- | --- |
| 订单行 / 摘要 | 业务名、稳定单号、当前状态以及此人最关心的数量。团员看“可领 X 颗”，老板看“已到账 X / Y 颗”。订单来源始终只有“直接派单”和“客户端下单” |
| 新单表单 | 客户选择游戏昵称、数量、预计交付时段及可选派单人，实时预估订单价。直接派单由派单人填写报价、核对模拟实收并确认发布。必须主动发布后才开放抢单 |
| 登录与验证码 | 延续已部署团员端的紧凑账号密码表单和可访问名称，必要字段完整后才打开图形验证弹窗。业务表单保留明确字段名与单位。共享账号选择须由用户主动触发 |
| 通知与抢单 | 成功发布后全团收到站内提醒。通知点击仅定位，接单区显示最新剩余量、公开或定向的承接权限。主动确认领取才改变份额。晚到、已领满、他人专属用文字解释 |
| 日报 | 显示当前承接人、本人可报份额、本次赠送次数及按时段算出的到账数。确认后刷新本单进度与客户视图。送完显示待结算，实际入账需要财务动作 |
| 金额与确认 | 分列原实付、拟补、实际补款、应退、实退和净付。老板作出决定、派单人登记到账或实退分别呈现。重要按钮写具体动作，例如“确认停送退款”“确认已到账” |
| 对话框与反馈 | 标题说明将执行的动作，正文列出对象与金额，提供取消和关闭。验证错误显示在当前操作处，保留已填值。键盘焦点可见，Esc 可退出，完成后可继续下一步 |

## 设计交付与验收

1. **区分三种进度。** 承接 50 颗只改变可抢份额。日报改变实际到账量。登记款项才改变实付或实退。前端展示及测试数据分别取值。
2. **验证角色可见性。** 客户只能看到本人订单及客户款项。派单员查看原实收和负责的订单，接单人查看可接份额及本人承接。演示身份切换仅供评审，正式产品按服务端授权。
3. **覆盖交互状态。** 原型可操作待派单、公开可抢、定向可接/不可接、已抢满、待确认、待补款、停送待退及已退。正式接入时还要补测加载、空列表、失败重试、离线、已撤回、权限失效及重复提交。请求成功后才显示资金或领取成功。
4. **实机验证。** 在手机底部安全区和软键盘、Pad 横竖屏与分屏、桌面键盘及浏览器返回下分别走一次业务。系统通知拒权或未到达时，用户仍可点「接单」。安装态的推送送达率与真实收退款另行验收。
5. **评审后落地。** 先确认接单队列的默认筛选、首页资金信息的顺序、各端 Tab 名称。评审意见更新到本规范和原型，再据此调整正式应用及预览图。支付渠道、同单自派自接、解锁退费等未决业务项继续在[业务细则](../heart-delivery.md)跟踪。
